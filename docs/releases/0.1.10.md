# FireCheck 0.1.10 submission release

FireCheck is an Android offline survey app for building, road and household fire-vulnerability assessments. This release brings the reviewed cleanup and multi-map work into the submission package.

## Android package

- Source version: `0.1.10+4015`.
- Download asset: `FireCheck-0.1.10-arm64-v8a.apk`, intended for GitHub tag `v0.1.10`.
- Requirements: Android 8.0 or later on ARM64. The project team must enroll the Google sign-in account in a published assignment to use the hosted demo.
- Expected Android version code: `6015` (`4015` base plus ARM64 offset `2000`). Verify the actual APK metadata, signature, size and hash before publishing.
- Update in place with the same signing certificate and a higher actual version code. Do not uninstall to work around an installation error; uninstalling deletes local data.

## Changes

Multiple downloaded maps can be selected for review and progressive upload of the signed-in user's changes. Accepted revisions remain in history and later edits can be submitted again. Direct-Drive job claims, revision supersession and account/credential/receipt binding protect against stale or concurrent work. The schema-v20 forward migration preserves upload history and file/receipt bindings.

The **New Feature** action provides building/road sketches with vertex validation, Undo and discard confirmation. A dashed orange outline distinguishes the read-only assignment boundary from blue edit geometry. Duplicate review provides a labeled offline geometry comparison, and survey requirement labels and completion checks follow the pinned form configuration. Download and upload screens provide clearer transfer progress and failure states.

Gateway source publication now rechecks source metadata and checksums and protects the advertised current version on failure. Output contracts and report-only orphan inventory tooling are documented. These changes do not authorize Drive folder moves or deletions.

## Recorded development verification

The reviewed source passed 1128 Flutter tests with zero failures/skips and 70 gateway tests, plus gateway typechecking. Full Flutter analysis reports the existing baseline of 931 diagnostics: 913 informational, 18 warnings, zero errors. It is not a clean analyzer result.

The same reviewed mobile source previously built as `0.1.9` / actual Android code `6014`, ARM64, at 47.72 MB. That signed APK updated the existing installation in place after approval. The observed walkthrough retained visible progress of 4 surveyed features out of 1438 across two maps; Home, map selection/zoom, unsaved sketch Undo/Cancel, Review after normal biometric authentication, an empty upload queue and same-account continuity passed. These UI observations do not prove exhaustive database integrity. The submission APK's new metadata and build must be checked separately.

The walkthrough did not finish/save a new survey or perform a real remote upload. Extended device and hosted capacity checks were explicitly deferred. Prior synthetic native tests and the private Drive/local PostgreSQL development publication probe have separate, bounded evidence; they do not establish hosted production capacity or all PRD acceptance. See the [full development record](../verification/2026-11-18-cleanup/README.md).

## Known limits and backend handoff

Direct-Drive fallback retries restart failed uploads rather than resuming a persisted transport session. Its process-global identity protection fails closed if the registry owner ends, including after a background isolate completes: a full app-process restart may be required. Reopening a screen or pressing Retry does not recreate that identity or steal an active claim. Separate-OS-process runners need additional liveness protection before introduction.

The forward migration [`20261118050717_authorize_photo_storage_mutations.sql`](../../supabase/migrations/20261118050717_authorize_photo_storage_mutations.sql) was verified against local fresh/upgrade fixtures, but was not deployed to the hosted backend. Mobile APK installation does not apply it. Backend operators must review the [cleanup decisions](../CODEBASE_TASK_CLEANUP.md), the [photo inventory](../../supabase/diagnostics/photo_storage_review.sql), required migrations and deployment before claiming rollout. Real Storage HTTP/GIS link acceptance remains unverified.

No staging walk, production backend rollout, historical Drive organizer operation or full field acceptance is claimed.
